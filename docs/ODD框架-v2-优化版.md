# ODD 框架 v2：Oracle-Driven Development（优化版）

> 基于《Go验货应对AI编程-2026-11-22.md》完整讨论优化整理。
> v1 散落在对话中（五个原则 + 红绿灰金循环）；v2 将讨论后期沉淀的关键洞察（oracle 腐化治理、伪慢层可观测、双侧验货、飞轮条件）结构化为**四个支柱**。

---

## 0. 一句话定义

**当写代码的边际成本趋零，"知道什么算对"成为唯一稀缺资源。**
ODD 把"定义对错"前置为可治理的资产，把"生成实现"交给 AI，用分层验货闭环保证 AI 的迭代不跑偏、可回溯、越转越快。

---

## 1. 核心思想：这次讨论沉淀的 6 条

1. **成本结构转移**：AI 消除的是"写"的偶然复杂性（Brooks）；"验"和"判断对错"的本质复杂性反而凸显。瓶颈从生成转移到验证与边界。
2. **真正的瓶颈是知识**：业务规则可以代码化，但规则的来源（事故、合规、财务口径）不在代码里。**知识采集与更新是核心工作量**，不是编码。
3. **验货必须分层**：不同层回答不同问题——快层验假设、伪慢层验集成、真慢层验真实世界。单层验货必然在"快而不真"和"真而慢"之间两头不靠。
4. **验货层也会腐化**：过期断言比没有断言更危险，因为它给出假绿。需要**二阶验货**：验货层自身可观测、可归因、可自动校准。
5. **验货是双侧契约**：不只有消费者侧建基础设施，还可以要求依赖方提供验货接口（可发现、可注入、可对账），把验货成本从单侧成本变成网络效应。
6. **飞轮靠案例撬动，不靠架构图**：冷启动用楔子场景拿三个数字（失败率、反馈时间、逃逸率），再用数据推组织共识和规范落地。

---

## 2. 框架主体：四个支柱

### 支柱一：知识层 —— Oracle 资产

**Oracle = 判断"什么算对"的机制**，必须元数据化，否则必然腐化。

三层 oracle（按可得性选择）：

| 类型 | 形态 | 例子 |
|---|---|---|
| 显式 oracle | 精确断言 | 主键唯一、金额汇总分毫不差、行数对账 |
| 隐式 oracle | 参照实现 | 新旧实现差分、影子运行对比（旧实现即 oracle） |
| 蜕变关系 | 性质断言 | 幂等（重跑结果不变）、单调性、边界变化规律 |

**Oracle 元数据四要素**（对治"过期断言比没有更危险"的唯一机制）：
- **来源**：哪次事故、哪条合规、哪次财务口径裁定
- **Owner**：谁负责更新
- **过期条件**：什么情况说明它可能失效
- **最后验证时间**：供新鲜度告警

**腐化检测**：规则对应的代码/配置变了、上游契约变了、owner 缺失、长期未验证 → 自动标黄，阻止 AI 在不可信 oracle 上迭代。

### 支柱二：边界层 —— 适配与契约

- **依赖面收敛**：插件直接碰的外部依赖必须个位数，全部收进 adapter（超时/重试/限流/幂等/错误分类/trace 统一封装）
- **窄接口**：插件只依赖稳定 port，不直接 import 二方包和 HTTP client
- **契约四件套**：schema、错误模型、幂等语义、版本兼容矩阵
- **契约冻结**：迁移/替换期接口不可变，实现可换（绞杀者模式 + 抽象分支）
- **语言分工**：Go 守硬边界（高频连接器、路由、统一错误模型），Python 守软长尾（业务逻辑、低频插件）；进程边界（gRPC/子进程），不用 cgo

### 支柱三：生成层 —— AI 受控迭代

- **受控迭代半径**：AI 只能改 adapter + core，不允许跨层大范围重构
- **门禁**：必须过快层才能推进；错误信息机器可读、分类统一
- **上下文窄化**：不给 AI 面对"多层 SDK + 大量 API"的原始混乱
- **人守三件**：业务事实来源、oracle 覆盖面、AI 观测不到的边缘事实

### 支柱四：信号层 —— 分层验货与自校准

**四层验货体系**：

| 层 | 频率/耗时 | 回答的问题 | 关键技术 |
|---|---|---|---|
| L0 快层 | 每次提交，秒级 | 代码与契约假设成立吗 | 类型检查、契约测试、导入冒烟、VCR/fake 回放 |
| L1 伪慢层 | 本地/CI，秒~分钟 | 集成路径与行为等价吗 | 容器化依赖、录制回放、差分对比、冷热边界样本 |
| L2 真慢层 | 低频，分钟~小时 | 真实世界偏差多少 | 影子运行、数据对账、真实 API 集成、性能容量 |
| L3 元验货层 | 持续 | 验货层自身可信吗 | 逃逸率、偏差率、替身新鲜度、owner 缺失告警 |

**关键交叉原则：数据温度（冷热）≠ 验货快慢。**
规则校验可以是快层（秒级），冷区数据操作可以是冷路径（低频批处理）；两者交叉决定资源形态（本地 CLI / 常驻服务 / 批处理 Job）。不要用一个维度拍板。

**核心循环：红 → 绿 → 灰 → 金 → 回流**

```
红：业务事实/契约变化 → oracle 变红（这是知识事件，不只是测试失败）
绿：AI 生成实现，快层秒级通过
灰：伪慢层跑集成路径、行为等价、冷热边界样本
金：真慢层对账、影子运行、灰度放量
回流：逃逸归因 → 修 oracle / 补样本 / 修契约 / 要求依赖方 → 回到红
```

**循环不闭合 = 只完成红绿，灰金缺位就是"假绿上线"。** 回流是 v2 补上的环节：归因结果必须能反向修改知识层和边界层，否则循环只是单向流水线。

## 3. 双侧验货：对依赖方的契约要求

| 层次 | 接口 | 回答的问题 |
|---|---|---|
| 可发现 | `/contract-probe` | 当前版本契约元数据 + 版本号（schema、错误码、超时/重试语义、限流策略） |
| 可注入 | 测试数据接口 | 受控测试模式：给定已知输入返回确定性输出，可模拟超时/限流/边界（与生产隔离） |
| 可对账 | `/replay-probe` + `/edge-cases` | 回放一致性校验码 + 权威边界条件清单 |

**核心价值：逃逸归因从"猜"变"可判定"**——探针不一致 = 依赖行为变了（契约要更新）；探针一致但验货失败 = 我们这边的问题（oracle 或实现）。

**范围边界**：内部二方包/服务可强制（写进上线 checklist）；第三方 SaaS 只能本地替身 + 真慢层兜底。不提供验货接口的服务，没人敢依赖——让验货接口成为上线竞争力。

---

## 4. 基础设施前提：硬前提 vs 可渐进

**硬前提（没有就转不起来）**：
1. 可执行的契约载体（schema/契约能被 CI 执行，不是文档）——没有它 oracle 无法自动触发
2. 契约代理 + 版本兼容矩阵——多依赖场景下"谁红了"的集中信号
3. 隔离可重复的测试环境——伪慢层的物理前提

**可渐进（楔子起步，逐步覆盖）**：
4. 数据对账管道（源/目标双端权限 + 调度 + 异常归因）
5. 影子运行（独立 worker + 差异分析库）
6. 规则注册与过期告警
7. 归因引擎（差异 → 哪层/哪条规则/哪个依赖）

---

## 5. 飞轮三脚与冷启动

**飞轮转起来的三个条件**：
1. **冷启动成本摊薄**：楔子场景的模板（oracle、伪慢层编排、探针、看板）被下一个插件直接复用——边际成本下降
2. **组织共识形成**：验货接口写进服务上线规范；逃逸率成为团队自关注指标（不是为了考核，是为了"敢让 AI 大面积迭代"）
3. **信号质量稳定**：逃逸率先治理到可信（宁可慢），再放开转速——信号质量是飞轮的刹车片

**冷启动三步**：
1. 一个楔子插件（依赖最乱、痛点最深的）跑通红绿灰金，沉淀可复用模板
2. 契约探针/验货接口写进内部服务上线 checklist（新服务必须有，老服务逐步补）
3. 拿出三个数字——失败率降多少、反馈时间降多少、逃逸率多少——撬动平台投入和组织共识

## 6. 投入判断（六项条件）

| 条件 | 值得投的信号 |
|---|---|
| 数据错误成本 | 高（金融/合规/核心报表） |
| 发布频率 | 高（每天多次） |
| 依赖面复杂度 | 多依赖、多插件、频繁变动 |
| 组织能力 | 有平台工程能力、能推动跨团队规范 |
| 楔子场景 | 有明确高痛点场景可先跑通 |
| 收益可量化 | 有基线数据、能在一个季度内证明 |

满足 ≥4 项：值得投；3 项：最小闭环谨慎投；<3 项：先解决更基础的问题。
**最小可行投入**：楔子插件闭环 + 验货接口规范 + 轻量规则注册表。先拿三个数字，再决定是否扩大。
**最危险的投法**：全面铺开、等收益显现——几乎必然烂尾。

## 7. 反模式清单

1. **盲迭代**：没有 oracle 就让 AI 生成实现
2. **假绿**：过期断言/过期替身给出错误绿灯
3. **宽依赖裸奔**：插件直接面对多层 SDK + 大量 API
4. **快层碰真实环境**：又慢又抖，反馈不可信
5. **真慢层缺失**：只有快层，测试全绿业务悄悄错
6. **只验代码不验数据语义**：编译通过、单测通过，口径和分区错了
7. **验货层不可观测**：腐化静默发生，逃逸率无人知道
8. **AI 大范围重构**：跨层改动绕过契约冻结
9. **把方法论当流程汇报而非门禁执行**：词汇丰富但红绿灯不亮——最典型的邯郸学步

## 8. ODD 与 TDD / DDD / SDD 的定位

| 方法论 | 时代约束 | 核心主张 | 与 ODD 的关系 |
|---|---|---|---|
| TDD | 人写代码 | 测试先行，红绿重构 | ODD 快层继承其红绿 |
| DDD | 领域复杂 | 领域模型是核心，统一语言 | ODD 战略层借用其限界上下文/防腐层 |
| SDD | AI 生成初期 | 规范先行，意图对齐 | ODD 吸收其规范思想，但补上了 SDD 管不了的**运行时噪声**与存量改造路径 |
| **ODD** | **AI 生成廉价** | **Oracle 先行 + 边界先行 + 分层验货 + 信号自校准** | **叠加层：AI 时代的验证操作系统** |

**ODD 不是取代它们，而是在"AI 让写变便宜"的新约束下重新配重**：边界从最佳实践变前置条件，验货从辅助变主战场，知识显性化从锦上添花变瓶颈环节。框架没变，权重变了。

---

## 9. 最终形态：验货从成本变成资产

- **开发者**：从写代码的人变成定义对错的人；新人通过 oracle 库理解系统设计（每条规则带来源和事故背景）
- **依赖方**：从黑盒变成可验货的白盒；验货接口成为服务上线竞争力
- **数据管线**：从"能跑就行"变成可信度可度量、可审计的基础设施（逃逸率、覆盖率、新鲜度进 SLO）
- **组织**：隐性知识显性化，组织记忆不再依赖老员工

> **最好的情况一句话：验货不再是瓶颈，而是飞轮的轴承。**
> 闭环靠逻辑成立，飞轮靠第一圈转起来的势能。飞轮的第一圈不是设计出来的，是推出来的。
