# 增量项目（greenfield）Playbook

核心矛盾：**没有历史代码可提取 oracle，规则全靠人定义；但契约和骨架在最便宜的时候不建，以后 retrofit 贵十倍。**

第一原则：**契约和骨架先行（便宜），oracle 覆盖面渐进（随业务定型扩）。不要反过来。**

## 阶段 0：依赖方契约先行（写第一行业务代码之前）

新插件/管线依赖内部服务时，先要求依赖方提供（或先定义好接口）：
- `/contract-probe`：契约元数据 + 版本（schema、错误码、超时/重试语义）
- 测试数据接口：受控测试模式（模拟超时/限流/边界，与生产隔离）
- 没有验货接口的内部服务 → 依赖评审时拦截，或外围先包 adapter

第三方 SaaS 没有验货接口 → 从第一天建 VCR 录制 + 真慢层对账计划。

## 阶段 1：CI 骨架先行（第一个 PR 就存在）

- `pyright` 严格模式 + `ruff` 进 CI 门禁（不过不许合入）
- 导入/注册/初始化冒烟（不调真实网络）
- 目录结构即边界：`adapter/`、`core/`、`plugins/` 分层；AI 改动半径用 CI 路径过滤强制，不靠自觉

## 阶段 2：规则注册表从第一天建

- 每条 oracle 登记元数据（source/owner/decay_condition/last_verified）
- **登记动作不能省，覆盖面可以渐进**：业务规则没定型前不追求全覆盖
- 轻量起步：YAML 头 + 看板 + 过期告警，不上重型治理平台

## 阶段 3：语言分工早决策

- 热路径（高频、要连接池、要低延迟）→ Go 常驻服务（gRPC）
- 一次性/低频/验证工具 → CLI（Go 或 Python）
- 长尾业务插件 → Python 子进程
- 进程边界、统一错误模型、统一可观测 schema 在第一个跨语言调用前就定好

## 阶段 4：分层渐进（随复杂度补，不预设全建）

- 上线前：快层 + 关键口径对账（金额/行数）
- 集成变复杂：补伪慢层（testcontainers、回放）
- 流量上来：补影子运行、灰度、漂移告警
- 每步补建前回到投入判断（框架 v2 第 6 节六项条件），不照搬全套

## 探索期豁免（增量特有，防过度工程）

业务未定型阶段（新口径、新分区策略试点）：
- 代码标 `exploratory: true` + `expires_at` + owner
- 豁免灰/金门禁，但快层必须过
- 到期两条路：定型 → 补 oracle 转正式；废弃 → 删除，不留主路径

**这条规则保护 ODD 的可信度**：探索性代码混进正式门禁，逃逸率立刻失真——验货层一旦不被信任，整套体系形同虚设。

## 增量特殊规则汇总

1. **先契约后实现**：验货接口是依赖评审的准入项，不是上线后的补丁
2. **骨架第一天**：CI 快层和目录边界从第一个 PR 强制
3. **登记不能省，覆盖可渐进**
4. **探索有豁免、有到期**：ODD 不惩罚试错，惩罚无期限的"临时"
5. **小管线不全建**：依赖少、发布低频的新管线，快层 + 关键对账就够，不照搬全部分层
