# 存量项目（brownfield）Playbook

核心矛盾：**有价值的隐含规则全在老代码、事故记录和日志里，而理解这一切恰恰是最大瓶颈。**

第一原则：**不试图一次性恢复全量规范（SDD 在 brownfield 的失败模式），一次只收敛一个能力。** 老实现是迁移期的 oracle，行为等价优先于"写得更好"。

## 阶段 0：依赖地图（1-2 天，决定后续一切）

对目标插件：
1. `pipdeptree` / 锁文件 → 列出直接依赖的二方包和 SDK
2. 扫描 `import`、SDK client 实例化、`requests.`/`httpx.` → 外部 API 调用点清单
3. 判定：直接依赖能否收敛到个位数？调用点是否有统一封装？

**退出标准**：一张依赖清单 + 标注哪些必须收进 adapter。
**红灯**：依赖面失控且无人能说清每个依赖的用途 → 停下叫人，不做代码改动。

## 阶段 1：边界收敛（最重的活，一次一个数据源）

- 选最痛的数据源/插件开始（楔子）
- SDK/HTTP 调用收进 adapter：统一超时、重试、限流、幂等键、错误分类、trace
- 插件改依赖 port 接口；core 转换逻辑抽成纯函数（不碰网络/存储）
- **旧代码不顺手重构**——只搬边界，不改行为

**退出标准**：该插件直接依赖全部经 adapter；扫描无散落调用点。
**红灯**：收敛中必须改行为才能搬 → 停下，先补 oracle（阶段 2）再搬。

## 阶段 2：Oracle 提取（顺序：代码 → 测试/小范围使用 → 日志）

1. **从代码提取**：把现有代码的隐含行为写成断言（空值处理、时区、幂等键算法）。注意：提取的是"当前行为"，不是"正确行为"——当前行为可能有 bug。登记时标 `confidence: extracted`。
2. **从测试和小范围使用记录校准**：已有测试、灰度记录、对账报表 → 标出哪些行为是有意为之，确认后升 `confidence: confirmed`。
3. **从日志迭代**：异常日志、事故复盘、对账差异 → 逐步修正 oracle。

**退出标准**：楔子路径的每条边界行为都有 oracle 覆盖。
**红灯**：提取中发现同一行为在不同路径不一致 → 停下叫人，这是业务口径冲突，AI 无权裁定。

## 阶段 3：契约冻结 + 双轨

- 冻结对外接口/schema（版本化，进版本矩阵）
- 之后任何实现替换（含 Go 化）必须满足：同输入同输出（差分测试）
- 旧实现保留为参照 oracle，直到新路径逃逸率连续数周为 0 才下线

**退出标准**：双轨对比机制运行中，差异可归因。
**红灯**：冻结后发现接口设计本身有问题 → 解冻走显式变更流程，不偷偷改。

## 阶段 4：分层补建（按需，不一次建全）

- 快层：pyright + ruff + 冒烟先进 CI（成本最低，最先做）
- 伪慢层：VCR 录制真实交互成可回放样本；补边界样本（空值/超大值/迟到数据）
- 真慢层：影子表/影子分区对账，先覆盖关键口径（金额、行数、主键）

**退出标准**：每层有明确频率和失败归因；逃逸率可计算。
**红灯**：伪慢层 flaky 率 > 5% → 降级或隔离，不许污染快层信号。

## 阶段 5：语言替换（可选，最后做）

仅当三个前提同时满足：契约已冻结 + 伪慢层覆盖该路径 + 该路径是热路径（高频/低延迟需求）→ 才考虑 Go 化。
进程边界 gRPC/子进程，不用 cgo；Go 侧复用同一套错误分类和 trace 字段；新旧路径同时进伪慢层验行为等价。

## 存量特殊规则汇总

1. **一次一个能力**：每个迭代周期只收敛一个数据源/一条链路
2. **旧实现就是 oracle**：迁移期行为等价优先
3. **提取 ≠ 正确**：`confidence: extracted` 的 oracle 必须经业务确认才能升级
4. **遗留服务包防腐层**：改不动的老服务，外围 adapter + VCR + 定期对账兜底，不追求完美
5. **允许"黄灯"路径**：很少变动的路径保持"快层过、伪慢层部分覆盖"即可，不强行全绿
6. **双轨期纪律**：冻结契约、差异归因、旧实现保留到逃逸率归零
